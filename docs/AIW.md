# AI文：一种保真优先的记忆压缩格式

> 这篇文章记录一个被数据反复纠正的过程：从「把记忆压短」出发，最后得到一个几乎相反的目标——**保住因果链，只是不写废话**。
>
> 所有数字都来自 `eval/` 下的实测数据（30 条记忆、93 个事实、200 道评测题、`deepseek-chat` 真 token），不是估计。

---

## 1. 起点：碎片摘要丢了什么

记忆插件普遍这么写注入内容：

```
尝试 JWT 鉴权失败，已回滚 session 方案。
```

短、便宜（210 token / 30 条），但丢了两个东西：

- **为什么失败**：refresh 轮换
- **失败长什么样**：登录失败

后果是可测的。我们造了 102 道「答案就在这条记忆里」的题（disc），只注入碎片时：

| 注入形态 | disc 答对率 |
| --- | ---: |
| 碎片摘要 | **0%** |
| AI文·题档 | 38% |
| AI文·轻档 | 77% |
| AI文·全档 | 87% |

**0% 不是笔误。** 碎片把所有可用于回答的边角信息都磨掉了，模型只能靠猜——而它猜不出「refresh 轮换」这种没人说过的词。

这就是本文的出发点：**压缩的代价不体现在 token 上，体现在「还能不能答对」上。**

---

## 2. 先划清它不是什么

设计过程中，有三个诱人的误解，每一个都被实测否掉。

| 误解 | 事实 |
| --- | --- |
| **是文言文** | 不是。文言追求古雅，AI文追求**词表命中**。`蒹葭苍苍` 6 token、`饕餮` 各 2–3 token——文言里最雅的部分，正是 tokenizer 里最贵的部分 |
| **是摘要** | 摘要压的是**语义**（丢信息），AI文压的是**形式**：虚词、语序、重复。一个字的信息都不丢 |
| **是压缩算法** | 实测只比原文省一点（全档 965 vs 原文 952），比碎片贵约 3 倍。它是**保真编码**，不是压缩器 |

所以它的定位是：**在保住因果链的前提下，最短的那一版。**

---

## 3. 规则：九条

| 编号 | 规则 | 做法 |
| --- | --- | --- |
| A1 | 删尽虚词 | 的/了/是/在/就/都/也/然后/其实/大概/一下 |
| A2 | 主体默认化 | 默认主体是「用户/本项目」；**只在切换主体时标** |
| A3 | 只用高频字 | 改·增·删·停·启·换·回·测·验·发·批·拒·败·成·卡·慢·稳 ✅　缮·厘·易·亟 ❌ |
| A4 | 关系符号化 | 见符号表 |
| A5 | **保真不删** | 否定 · 数量 · 时间 · 条件（若/则/除非）· 情态（必须/不要/可）· 专名与标识符（URL/路径/错误码/版本/API 名，**原样保留**） |
| A6 | 一行一断言 | 两个断言不能合并——合并了就没法单独失效、单独回源 |
| A7 | 尾部三元 | `@时间 #来源 !置信`（`!` 高 · `?` 中 · `~` 低） |
| A8 | 禁表 | 典故、成语、生僻字、之乎者也 |
| A9 | **符号优先，语言不换** | 见 §8 |

### 符号表

| 符号 | 含义 | 例 |
| --- | --- | --- |
| `→` | 导致 / 变成 | `正斜杠→配置读败` |
| `←` | 来自 | `403←缺tenant头` |
| `=>` | 推出 | `多实例=>不一致` |
| `=` | 定义 / 等同 | `后端=老王` |
| `+` `-` | 增 / 删 | `必通登录+支付` |
| `~` | 约 / 近似 | `~3天` |
| `@` | 时间 | `@2026-10-24` |
| `#` | 来源（回 L0） | `#12` |
| `!` | 红线 / 高置信 | `!禁无备份迁移` |
| `?` | 未决 / 中置信 | `?缓存未定` |
| `□` | 待办 | `□补测试` |
| `vs` | 对比 | `Redis vs 本地LRU` |

### 三档只有尺寸不同

| 档位 | 汉字上限 | 典型用途 |
| --- | ---: | --- |
| 题 `title` | 12 | 标题、指针、Outline 节点 |
| 轻 `lite` | 45 | 分页首批、低预算注入 |
| 全 `full` | 45 | 证据包正文 |

一条真实的 AI文：

```
改登录鉴权→JWT，refresh轮换→登录失败，故回滚session。@2026-10-24 #12 !
```

## 4. 第一次实测：token 账

30 条记忆、93 个事实，`deepseek-chat` 真 token：

| 形态 | token | 相对原文 |
| --- | ---: | ---: |
| 原文（L0） | 952 | — |
| 碎片（旧方案） | 210 | −78% |
| AI文·题 | 247 | −74% |
| AI文·轻 | 533 | −44% |
| AI文·全 | **965** | **+1.4%** |

**注意最后一行：全档比原文还贵。**

原因很快查清：`@2026-10-24 #12 !` 这类尾部元数据被算进了正文。而尾部是**记账数据**（谁在什么时候说的、可信度多少），不是记忆内容——它该进数据库，不该进上下文。

顺带发现一件事：宿主自带的 token 计量按 `CHARS_PER_TOKEN = 4` 估算，对中文**低估了 2.07 倍**（它以为这批原文是 461 token，实际 952）。所以「便宜不便宜」必须用真 tokenizer 量，不能信估算。

---

## 5. 被数据逼出来的改法：剥掉尾部

| | token | disc 答对 |
| --- | ---: | ---: |
| 含尾 | 965 | 90% |
| **无尾** | **665** | 89% |

**省 31%，准确率掉 1 个百分点。**

1pp 落在噪声内——同一配置连跑两次，base 那列就波动 4pp。于是定下一条铁律：

> **尾部是记账数据，不是记忆内容。入库时拆成结构化字段（`validFrom` / `source` / `confidence`），注入时剥掉。**

这条规则后来在实现里变成一个硬约束：**剥离动作只在 `ingest()` 里发生一次**，任何别的路径都不许再碰尾部。

---

## 6. 保真与答题：三档的真实代价

| 注入形态 | 事实保真 | token | disc 答对 | base 答对 |
| --- | ---: | ---: | ---: | ---: |
| 原文 | 96.8% | 952 | — | — |
| AI文·题 | 61.3% | 247 | 38% | 61% |
| AI文·轻 | 91.4% | 533 | 77% | 70% |
| AI文·全 | 97.8% | 965 | 87% | 74% |
| AI文·全·无尾 | 97.8% | **665** | **89%** | 74% |
| 碎片 | 21.5% | 210 | **0%** | 74% |

（`base` = 记忆里和目标都有答案的 23 道题，用来测会不会「因为注入了记忆反而变差」。）

三档的关系从此清楚：

- **题档**（247 token）只够「找得到」，不够「答得对」——38%
- **轻档**（533 token）是性价比拐点——77%
- **全·无尾**（665 token）是保真上限——89%

**665 token 买到 89%，比 210 token 买到 0% 划算得多。**

## 7. 符号表：收益会随规模缩水

AI文 的第一次失败里，有两次是「读不懂符号」，不是「没有信息」。于是在系统提示里加了一张约 60 token 的符号表：

| 题量 | 无符号表 | 有符号表 | 差 |
| ---: | ---: | ---: | ---: |
| 12 题 | 75% | 92% | **+17pp** |
| 200 题 | 87% | 90% | **+3pp** |

**样本一扩大，收益就从 +17pp 掉到 +3pp。**

这不是符号表变差了，而是 12 题那批恰好极端依赖符号。教训很直接：

> **小样本上的「显著提升」，多半是小样本的偏差。**

所以符号表留在了系统提示里（+3pp 也是收益，成本 60 token），但不再作为设计卖点。

## 8. 反例：混合语言并不省 token

一个很自然的想法：既然要省 token，那就用最省的语言写——英语、日语、韩语，怎么省怎么来。

逐词实测 42 个概念，结论是反的：

| 概念 | 中文 | 英文 | 结果 |
| --- | ---: | ---: | --- |
| 鉴权 | 2 | auth = 1 | 英文省 1 |
| 超时 | 2 | timeout = 1 | 英文省 1 |
| 嵌套 | 1 | nest = 1 | 打平 |
| 回滚 | 2 | rollback = 2 | 打平 |
| 迁移 | 1 | migrate = 2 | **中文更省** |
| 禁止 | 1 | forbid = 2 | **中文更省** |

**42 个概念里只有 3 个真能省，4 个反而更贵，其余打平。**

根本原因：DeepSeek 是中文模型，对双字词的合并非常激进（`鉴权`/`嵌套`/`校验` 都压到 1 token）。**换语言的收益空间，已经被分词器本身吃掉了。**

所以 A9 从「任何语言都可以」收窄为：

> **符号与标识符优先（`→` `=` `!` `@` `#`、`JWT` `ENOENT`）；语言替换必须逐词实测，默认不做。**

唯一不受语言影响的收益是**符号**——它们在任何分词器上都是 1 token，而且语义最硬。

## 9. 生成侧：约束提示词比「让它压缩」有用

AI文 要由模型生成，但直接说「请用 AI文 重写」的失败率极高。

改法是把 `must_keep` **前移**：先用规则抽出必须保住的事实（标识符、数字、否定、条件），在生成**之前**把它们写进指令。

第一版的实测结果很糟——**通过率 100%，但生成的长度是人工的 1.5–2 倍**，也就是「压了，但没压短」。

抽查三条，两个具体缺陷：

```
m03 生成：「bug」：Windows 路径拼接用正斜杠→配置文件读不到→错误「ENOENT」…
m03 人工：Win路径拼正斜杠→配置读败（ENOENT）；仅打包后现，dev正常；修=path.join。
```

1. **引号泄漏**：指令里写「必须原样出现：「ENOENT」」，模型把「」当成了要输出的内容
2. **点被吃**：指令里有 `.env.local`，生成成 `env.local`，开头的点丢了

修法是把约束换成纯文本清单 + 三条硬规则：

```
必须原样保留这些词（它们只是校验清单，不要在输出里加引号）: ENOENT / path.join
· 标识符要连标点一起保留：.env.local 开头那个点
· 长度上限：54 个字符。超了就等于没压缩。
```

修完：

| 约束口径 | 通过 | 一次通过 | 平均尝试 | 压缩比 |
| --- | ---: | ---: | ---: | ---: |
| rule（只用规则抽的事实） | 100% | 93% | 1.1 | **1.06×** |
| human（给人工资讯） | 100% | 100% | 1.0 | 1.02× |

**1.06× 意味着生成和人工写的一样长。** 从这里开始，AI文 才是「可以交给模型写」的格式。

> 教训：**约束提示词本身也需要被测量。** 它优化的是模型的理解，不是模型的行为——「引号会被抄进输出」这种事，只有跑一遍才知道。

## 10. 落地时踩到的三个坑

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 「高」写不进尾部，报格式错 | 置信只认 `! ? ~` | 同时接受 `高 中 低` |
| 标点差异产生两条记忆 | id 用原文算 | 改用**内容指纹**（忽略标点空白） |
| 问「Kubernetes」召回 docker 条目 | 拉丁词被切成 `er` 撞车 | 拉丁/数字整段入索引，只对中文切 bigram |

第二个坑尤其说明问题：`预发端口 8081；上线前必跑 smoke` 和 `预发端口 8081，上线前必跑 smoke` 被当成两条记忆——**格式的严格性必须配合语义上的去重**，否则条目会随标点漂移而膨胀。

---

## 11. 结论与边界

**AI文 适合什么：**

- 需要保留因果链的事实/决策（「为什么失败」「后来怎么修的」）
- 要长期复用、跨会话召回的断言
- 会被注入系统提示、成本和保真都要管的内容

**不适合什么：**

- 长文、文档、日志——那是另一层（项目档案）
- 需要逐字还原的对话——那是原文归档（L0）的事
- 纯代码或结构化数据——AI文 的符号表帮不上忙

**一句话总结：**

> **AI文 不是把话说短，是把话说准。**
> 它接受「比原文贵一点」，换取「答对率从 0% 到 89%」；它拒绝「靠换语言省 token」，因为分词器已经把这部分收益吃掉了；它把尾部元数据赶出正文，因为那 31% 的 token 买不到任何准确率。
