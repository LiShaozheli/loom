# AI文：为什么我要给记忆发明一种格式

这篇是写给三个月后的自己看的。里面有多少坑、多少错判，我都照实写。

---

## 起因：我测出了一个 0%

做记忆插件的时候，我看了一圈同类产品，注入的内容基本长这样：

```
尝试 JWT 鉴权失败，已回滚 session 方案。
```

很干净，也很省 token。30 条记忆一共 210 个 token。当时我觉得这就是答案：把历史压成一句结论，下一轮塞回去，成本低，信息也在。

后来我拿这 30 条记忆出了 102 道题，每道题的答案都只存在于某一条记忆里。比如「登录接口当初为什么回滚」。

结果：**102 道，对 0 道。**

不是模型笨。是那句话里根本没有「为什么」。它只说「失败了」，没说「因为 refresh 轮换失败」。模型再怎么推理也推不出来，因为那个信息在压缩的时候就被磨掉了。

这件事定了整个项目的调子：**压缩的代价不体现在 token 上，体现在「还能不能答对」上。** 一句看起来信息完整的结论，可能已经把可复用的部分丢干净了。

所以问题变成了：**有没有一种写法，比碎片长，但把因果留住？**

---

## 为什么不是文言文

我第一个念头是文言文。字少、信息密度高，看起来很对。

在 tokenizer 上试了两下就放弃了：

```
蒹葭苍苍      → 6 token
饕餮          → 2–3 token
```

文言里最讲究的部分，生僻字、典故、单字动词，**恰好是词表里最贵的部分**。而且它对现代工程语境几乎没有帮助：`refresh 轮换` 没法用一个字表达，`ENOENT` 也不存在古称。

更重要的是，文言追求的是「雅」。我要的是「准」。这两个目标在这里是冲突的：为了雅而选的字，往往是为难 tokenizer 的字。

所以「AI文」这个名字，一开始其实叫文言文压缩，后来被数据逼着改了。它跟文言没关系，它只是**用词表认识的字，写清因果和约束**。

有意思的是，我后来意识到，我参考的对象根本不是古文，而是**事故复盘里那条一行字的结论**：

```
改登录鉴权→JWT，refresh轮换→登录失败，故回滚session。
```

复盘必须保留因果（为什么失败）、必须能追到证据（谁在什么时候说的）、不能有形容词（那些是判断不是事实）。这三条，就是 AI文 的全部设计意图。

---

## 一条记忆长什么样

```
改登录鉴权→JWT，refresh轮换→登录失败，故回滚session。@2026-10-24 #12 !
```

拆开看，它做了三件事：

**一、删掉不承载信息的词。** 的、了、是、在、然后、其实、大概，这些在中文里占了不少字数，删掉不影响理解。

**二、把关系变成符号。** `→` 表示导致，`=` 表示等同，`!` 表示红线或高置信，`?` 表示未决。这不只是为了短：符号在所有分词器上都是 1 个 token，而且比「导致」这种词更硬，不会有歧义。

**三、把元数据挪出正文。** 末尾的 `@时间 #来源 !置信` 是记账用的：这条什么时候、谁说的、可信度多少。它不该出现在注入内容里（下面会讲，这一步省了 31% token）。

有几样东西是**绝对不能删**的：否定、数量、时间、条件（若/则/除非）、情态（必须/不要/可以），以及所有专有名词和标识符。

最后这条吃过亏。有一次我把 `path.join` 写成 `路径拼接`，看起来更通顺，但下次要修 bug 的时候，模型还得自己猜是哪个 API。标识符必须原样留着。它贵，但它唯一。

---

## 第一次算账：越保真越贵

把 30 条记忆全部写成这种格式，然后用 `deepseek-chat` 的真 tokenizer 数：

| 形态 | token |
| --- | ---: |
| 原文 | 952 |
| 碎片（旧方案） | 210 |
| AI文（带尾部） | **965** |

**比原文还贵。**

这个结果挺打击人的。我的出发点是想省，结果做出来一个 1.4% 的通货膨胀。

顺便说个意外发现：宿主自带的 token 计量是按「4 个字符 = 1 token」估的，对中文**低估了 2.07 倍**：它以为这批原文是 461 token，实际是 952。所以这类事不能信估算，得用真 tokenizer 量，否则你会在一个错误的基础上做所有决策。

贵在哪，很快就查出来了：`@2026-10-24 #12 !` 这些尾巴被算进了正文。30 条记忆，每条尾巴几十个字符，加起来就是 300 个 token。

但尾巴是必需的。没有来源，记忆没法追溯；没有置信度，没法排序。

所以问题不是「要不要尾巴」，而是「尾巴该放在哪」。

---

## 把尾巴砍掉

答案很土：**尾巴该进数据库，不该进上下文。**

入库的时候把它们拆成三个字段（`validFrom` / `source` / `confidence`），注入的时候只送正文。

| | token | 102 道 disc 题答对 |
| --- | ---: | ---: |
| 带尾巴 | 965 | 90% |
| **不带尾巴** | **665** | 89% |

**省了 31%，掉了 1 个百分点。**

1 个百分点在噪声范围内：同样的配置连跑两次，另一组回归题的波动就有 4 个百分点。所以我认了这个交易。

这件事后来变成了代码里的硬约束：**剥离尾部只允许在 `ingest()` 里发生一次**。别的任何地方都不许再碰格式，否则早晚会出现「有的地方剥了、有的地方没剥」，然后你会看到同一个库里有两种长相的记忆。

---

## 三档：不是所有地方都值得放全档

一套格式用到底是不现实的。标题只需要「找得到」，证据包需要「答得对」。所以定了三档，规则完全一样，只有尺寸上限不同：

| 档 | 汉字上限 | 用途 |
| --- | ---: | --- |
| 题 | 12 | 标题、指针、目录节点 |
| 轻 | 45 | 分页首批、低预算注入 |
| 全 | 45 | 证据包正文 |

实测三档的真实差别（同一批 200 道题）：

| 注入形态 | token | disc 答对 |
| --- | ---: | ---: |
| 碎片 | 210 | **0%** |
| 题 | 247 | 38% |
| 轻 | 533 | 77% |
| 全·无尾 | 665 | **89%** |

这组数字回答了一个很实际的问题：**预算该给多少。**

- 只有 247 token 可用时，就别指望答对，只适合做目录
- 533 是性价比拐点
- 665 拿满

**665 个 token 换 89%，对比 210 个 token 换 0%，这笔账不用算。**

---

## 符号表这件事，我一开始高估了

AI文 的失败样本里，有一半不是「没有信息」，而是「模型读不懂符号」，它不知道 `→` 在这里是「导致」。

于是我往系统提示里加了一张符号表，大概 60 token。小样本上效果惊人：

| 题量 | 无符号表 | 有符号表 |
| ---: | ---: | ---: |
| 12 题 | 75% | **92%** |
| 200 题 | 87% | 90% |

从 +17pp 掉到 +3pp。

我当时的判断错在：拿 12 道题的结果当结论。那 12 道恰好极端依赖符号语义，放大到 200 道之后，收益被摊平了。

符号表我留下了。+3pp 也是收益，成本才 60 token。但我不再把它当卖点。**小样本上的显著提升，多半是小样本的偏差。**

---

## 语言混写：我试过，失败了

有个想法很自然：既然要省 token，那就怎么省怎么来，英语、日语、韩语，哪个词便宜用哪个。

我逐个量了 42 个概念：

| 概念 | 中文 | 英文 | 结果 |
| --- | ---: | ---: | --- |
| 鉴权 | 2 | auth = 1 | 英文省 1 |
| 超时 | 2 | timeout = 1 | 英文省 1 |
| 嵌套 | 1 | nest = 1 | 打平 |
| 迁移 | 1 | migrate = 2 | **中文更省** |
| 禁止 | 1 | forbid = 2 | **中文更省** |

42 个里只有 3 个真能省，4 个反而更贵，其余打平。

原因很简单：DeepSeek 是中文模型，双字词合并得非常激进（`鉴权`、`校验`、`嵌套` 都是 1 token）。**换语言能省的那部分，早就被分词器自己吃掉了。**

所以我把规则从「任何语言都可以」收窄成：

> 符号和标识符优先（`→` `=` `!` `JWT` `ENOENT`），语言替换必须逐词实测，默认不做。

唯一不受语言影响的收益是符号。它在哪个 tokenizer 上都是 1 token，而且语义最硬。

---

## 让模型来写，第一版是失败的

格式定好了，接下来的问题是：谁来写？

手写不现实。每天几十条记忆，人不会那么勤快。所以我试着让模型按格式生成，把必须保住的事实（标识符、数字、否定、条件）在生成**之前**就写进指令，而不是生成后再检查。

第一版：**通过率 100%，但长度是人工写的 1.5–2 倍。**

也就是说，格式对了，压缩没了。抽两条看：

```
生成：「bug」：Windows 路径拼接用正斜杠→配置文件读不到→错误「ENOENT」……
人工：Win路径拼正斜杠→配置读败（ENOENT）；仅打包后现，dev正常；修=path.join。
```

两个具体毛病：

**引号被抄进输出。** 我在指令里写「必须原样出现：「ENOENT」」，模型把引号当成了要输出的内容。

**点被吃掉。** 指令里给了 `.env.local`，生成成 `env.local`，开头的点被当成标点了。

修法很笨：把约束改成纯文本清单，明确说「这些只是校验清单，不要在输出里加引号」，再补一句「标识符要连标点一起保留」，最后加一条硬上限「长度不超过原文的 45%」。

改完：

| 口径 | 通过 | 一次通过 | 压缩比 |
| --- | ---: | ---: | ---: |
| 只用规则抽的事实 | 100% | 93% | **1.06×** |
| 给人工资讯（上界） | 100% | 100% | 1.02× |

1.06× 意味着生成的和人工写的一样长。到这里，AI文 才算是「可以交给模型写」的格式。

**教训：约束提示词本身也需要被测量。** 它优化的是模型的理解，不是模型的行为。「引号会被抄进输出」这种事，光看提示词是看不出来的。

## 落到工程里，它真正带来的东西

格式好不好看是次要的，重要的是它在代码里换来了什么。

**一、可以逐条失效。** 一行一个断言，所以「这条过时了」可以精确到一条，不用把整段记忆推翻重写。如果两条断言写在一行，冲突处理就变成全有全无。

**二、双表示。** 每条记忆存两份：`body`（白话原文）+ `aiw`（压缩版）。注入用 `aiw`，审计、迁移、换模型用 `body`。**压缩不能是唯一的真相形态**。哪天模型换了、tokenizer 变了，你还能回到人话。

**三、写入时可以拒绝。** 因为格式是机器可校验的，所以能在入口就拦下来：格式不对、缺来源、关键事实丢了、编造了标识符，四种情况直接拒。这比「先写进去，等发现不对再改」便宜得多，因为错误记忆一旦进入注入流，每一轮都在误导模型。

**四、去重。** 一条记忆的身份由**内容指纹**决定（忽略标点和空白），不是由原文决定。否则 `预发端口 8081；上线前必跑 smoke` 和 `预发端口 8081，上线前必跑 smoke` 会变成两条记忆，库会随标点漂移而膨胀。

**五、预算可算。** 有了三档和实测数字，注入多少是可以算的：665 token 换 89%，533 换 77%，247 只够做目录。做产品的时候，这个换算比「感觉差不多」有用。

---

## 它不擅长什么

- **长文。** 文档、日志、会议纪要塞不进 45 个汉字，那是另一层的事。
- **逐字还原。** 要引用原话，就该去查原文归档，而不是指望压缩版。
- **代码和结构化数据。** 符号表在这上面帮不上忙。

还有一件要说清楚：**AI文 不便宜。** 全档 665 token，是碎片的三倍。它值得，只是因为碎片答对率是 0%。如果哪天碎片能答到 70%，这笔账就得重算。

---

## 如果重来

三件事我会更早做：

**一、先做评测，再设计格式。** 我一开始花了很久讨论「文言文好不好」，其实只要 200 道题、一晚上，就能知道这条路走不通。

**二、先量 tokenizer，再谈省不省。** 我对中文 token 成本的直觉，两次都是错的（一次以为文言省，一次以为英文省）。

**三、把「知识」和「记账」分开。** 尾部元数据占了 31% 的 token，但它一个字的信息都不贡献给回答。这件事我想了两天才想明白，其实第一天就该问：这些字段是给谁看的？
